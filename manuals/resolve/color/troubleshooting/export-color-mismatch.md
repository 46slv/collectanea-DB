# 書き出し後に色や明るさが違うとき

Colorページでは自然に見えていたのに、書き出した動画を開くと明るい、黒が浮く、彩度が違う、と感じることがあります。こうした差は、**書き出された画像信号が変わった場合**と、**同じファイルを再生環境が違う見え方で表示している場合**を分けなければ原因を特定できません。

本記事はDaVinci Resolve 21.1を対象に、納品用ファイルの色を切り分ける手順を扱います。21.1固有のDeliver設定名や数値の推奨値を確定するものではありません。[納品前のColor QC](../recipes/pre-delivery-color-qc)で扱う補正漏れ・ショット間の違いと、ここで扱う**Resolve内と実ファイル／外部プレーヤーとの差**は、別の検査です。

## まず差が発生する場所を特定する

| 見える症状 | 最初に比較するもの | すぐには断定できないこと |
| --- | --- | --- |
| 別の動画プレーヤーでだけ明るい | 同一ファイルをResolveへ再読み込みした映像と外部プレーヤー | 書き出し時に明るさが変わったとは限らない |
| Resolveへ再読み込みしても階調が違う | 元タイムラインと書き出しファイルの、入力解釈をそろえた比較 | エンコーダーが原因とは限らない |
| 全ショットが一様に薄い・濃い | Output変換、色空間／ガンマの情報、表示条件 | Clipノードだけの誤りとは限らない |
| 特定カメラ・ショットだけ違う | Input、Clip／Group／Timeline補正、書き出し対象 | 共通のOutputだけが原因とは限らない |
| HDR素材をSDRとして見ると大きく違う | 納品仕様、SDR／HDR変換、再生環境 | 一つのガンマ値を変えれば解決するとは限らない |
| 黒や白の近くで階調が変わる | Levelsの解釈、Output変換、エンコード、Scopes | モニターだけが原因とは限らない |

「色ズレ」は症状名であって原因名ではありません。最初はグレードを変更せず、問題のあるフレームを決めます。比較するファイル名、再生アプリ、モニター、表示モードを記録し、**同じファイルの同じフレーム**を比較できる状態にします。

## 1. 納品条件とColor Managementを固定する

まず納品先が要求する色域・伝達特性、SDR／HDR、ファイル形式、解像度、フレームレートを確認します。案件指定がない場合、対象の表示環境を決めずに「正しい見え方」を一つに定めることはできません。

次に[カラーマネージメントの基礎](../learn/color-management-basics)に沿って、Project SettingsのColor Managementを確認します。

1. **Input**：撮影素材の色域とLog／ガンマは何か。表示用へ変換済みのファイルをカメラLogとして再解釈していないか。
2. **Timeline**：どの作業空間で補正しているか。異なるカメラのInputがそれぞれ正しいか。
3. **Output**：納品先に向けた変換はどこにあるか。RCM／ACESの設定か、手動のCST／LUTか。
4. **変換の重複**：Project側のOutputとClip／Group／Timelineに置いた出力CSTや表示用LUTが、同じ役割を二度担っていないか。
5. **表示経路**：ResolveのViewerと外部モニターが同じ処理・校正条件で見られているか。

[Timelineグレーディング](../reference/timeline-grading)や[Group Grading](../reference/group-grading)の補正も画像に作用します。全カットで同じ症状なら共通処理、特定のカメラだけならInputとGroupを先に調べます。ただし、これは優先順位であり、症状から原因を確定する規則ではありません。

**「Rec.709」の名前だけで表示条件は確定しません。** 色域とガンマ／伝達特性は分けて記録します。HDRのPQ／HLGをSDRと同じ表示条件で比べたり、未確認のガンマ値を汎用の推奨値として使ったりしないでください。

## 2. 書き出した実ファイルを確認する

Deliverページなどで書き出したファイルについて、プリセット名だけでなく実際の出力結果を確認します。Blackmagic Designの公式Mediaページは、Resolveが複数の書き出し形式とエンコードオプションを扱うことを紹介しています。しかし、プリセットを選んだだけでは個々の納品ファイルの色が正しいと証明できません。

1. **実ファイル名・保存先・作成日時**を確認します。古いレンダーや別バージョンを開いていないか調べます。
2. 出力範囲、解像度、フレームレート、コンテナ／コーデックを確認し、元タイムラインと対応付けます。
3. ファイルから読み取れる色空間・ガンマ等のメタデータを確認します。項目が存在するか、どの値が埋め込まれるかは形式とResolve版ごとに確認が必要です。**色タグがあることと、画素に正しいOutput変換が施されていることは別です。**
4. 肌、暗部、ハイライト、空のようなグラデーション、カット境界を再生します。階調の帯や圧縮ノイズがある場合は、色管理だけでなくエンコード品質も調べます。
5. 同じファイルを複数アプリで開くなら、アプリとモニターを記録します。「別のファイルを比較した」のか「同一ファイルの表示が違う」のかを分けます。

Video／Data Levelsなど信号レンジの解釈が異なると、黒や白付近の見え方が変わる可能性があります。ただし、レンジ指定の場所と推奨値は納品条件・形式に依存します。薄く見えるからといって無条件にFull／Videoを切り替えず、ファイルと再生側の解釈を確かめます。

## 3. 書き出しファイルをResolveへ再読み込みする

同じアプリの色管理下で比較すれば、外部プレーヤー固有の表示差をある程度分離できます。ただし再読み込みにもInput変換がかかり得るため、比較条件をそろえる必要があります。

1. 実際に納品するファイルをMedia Poolへ読み込み、元タイムラインの代表フレームと比較できる状態にします。
2. **再読み込みしたファイルのInput解釈を確認**します。納品色空間へ変換済みの映像へ、撮影時のカメラLog Inputをもう一度適用しないでください。
3. 再読み込み映像へ元のClipグレード、Group補正、TimelineのLook、出力CSTが**重ねて適用されていないか**確認します。変換済みの画像を二度処理すると、書き出し品質の検査になりません。
4. Viewerで同じフレームを交互に表示し、[Scopes](../reference/scopes)のWaveform／RGB Paradeも比較します。Scopesの単位・表示範囲と処理位置が異なる場合、数値の単純比較はできません。
5. 差が残る場合、同じ範囲を短く再出力します。一度に変更する条件を一つに絞り、再現性を調べます。

**再読み込みで一致しても、すべての外部再生環境で一致する証明にはなりません。** 逆に、再読み込みで違って見えた場合は、先に二重変換や比較位置の相違を除外してください。

## 4. Resolveで一致するなら表示環境を調べる

Resolveへ戻したファイルが期待に近いのに、別プレーヤーだけ明るく見える場合、表示経路の違いを確認します。

- ファイルの色空間・ガンマ等のメタデータを、両アプリがどう解釈しているか。
- OSのディスプレイ色管理、モニタープロファイル、HDR表示モード、外部映像出力の経路が一致しているか。
- プレーヤーのデコード処理、表示変換、トーンマッピングが関与していないか。
- 同じモニター、明るさ設定、環境光で比較しているか。

ResolveのViewerと別アプリの動画を横に並べても、両アプリの表示変換が一致する保証はありません。**外部プレーヤーでの差を打ち消すために、プロジェクト全体のグレードを一律に変えるのは避けます。** 別の再生環境では逆方向にずれる場合があります。対象環境での試験と納品仕様を優先します。

OS固有の表示補正や固定ガンマ値は、21.1実機と配布先で確認するまで本記事では推奨しません。

## 5. Resolveへ戻しても違うなら出力までを調べる

再読み込みのInputと補正経路をそろえても差が残る場合、次を順に確認します。

| 点検場所 | 確認する内容 | 比較の方法 |
| --- | --- | --- |
| Output変換 | RCM／ACES／CST／LUTの担当と重複 | 元設定を記録し、一箇所ずつ切り分ける |
| ショット単位 | Clip、Group、Timelineの適用範囲 | 問題ショットと正常ショットを比べる |
| ファイル解釈 | 色タグ、再読み込み側Input、Levels | 正しい入力条件で比較し直す |
| エンコード | 形式、品質設定、信号レンジの扱い | 短い区間を検証用設定で出力して差を見る |
| 時間の不一致 | 古い出力、異なるフレーム、動的な補正 | 同じ時間位置のフレームへ固定して比べる |

変換を試験目的で無効化するときは、元の状態を記録し、確認後に復元します。「CSTを切ると近づく」はCSTの位置と設定を再検討する手掛かりですが、CSTが不要だと決まったわけではありません。また、画面全体の明るさが違う場合と、細かな色境界に圧縮のにじみがある場合は、原因の優先順位が異なります。

## 判断例

### 例A：Resolveでは正常、別プレーヤーだけ明るい

SDRのインタビューを書き出し、Resolveに再読み込みした映像は元のViewerと近いのに、別プレーヤーでは顔も壁も明るく見えるとします。まず出力ファイルと比較フレームを特定し、再読み込みで余計なInput変換がかかっていないことを確認します。

条件が整っていれば、プレーヤー側の色タグ解釈、表示変換、モニタープロファイル、HDR設定を比較します。**この段階でClipグレードを暗くする必要は確定していません。** 配布先の表示条件が決まっているなら、そこでの試験結果を判断根拠とします。

### 例B：Log素材の一部だけ彩度が不自然

LogのAカメラと、すでに表示用へ変換したBカメラが混在する編集を想定します。B素材だけ過度なコントラストになった場合、BへAと同じLog Inputを割り当てていないか確認します。さらにBのGroupにInput CSTがあり、プロジェクト側でも同じ目的の変換をしていないか調べます。

入力解釈と変換の役割を整理してから、同じ納品設定で短い区間を再出力します。補正量を先に弱めるより、**何を入力とみなし、どの段階で納品先へ変換したか**を確認する方が原因を特定しやすくなります。これは仮想例であり、21.1実機での再現検証ではありません。

## 最終確認と記録

原因が特定できたら、元のタイムラインと最終出力ファイルの両方を再検査します。最低限、該当クリップとフレーム、Input／Timeline／Output、CSTやLUTの役割、実ファイル名と形式、色空間・ガンマに関する情報、再生アプリ・モニター、修正前後の比較結果を残します。

画面上だけで終了判定せず、**実際に納品するファイルを想定環境で確認する**ところまでをQCとします。必要な信号レンジ・コーデック・タグ・トーンマッピングは案件の納品仕様を正本とし、この記事の例を固定プリセットとして適用しません。
