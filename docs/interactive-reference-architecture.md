## 目的と責務

COLLECTANEAに「読んで、見て、操作して理解する」教材を段階的に追加する。映像・画像処理が最初の題材だが、将来は音響、時間・アニメーション、ソフトウェア操作、実機を模したスイッチャー／ミキサーにも使用する。

- **Reference索引**: 用語を探す入口。技法・観察できる現象を短い日本語で説明する。未実装の個別ページへリンクしない。
- **概念ページ**: 技法の仕組み・適用条件・実験から読み取れる差・参考資料を説明する正本。
- **ソフト別ガイド**: AE / Resolve / Fusion等での確認済みの実現方法を説明する。概念と製品機能の一対一対応を保証しない。
- **インタラクティブ教材**: 処理結果や音・動作・機器状態を実際に変えられるUI。解説本文とは分離したReactコンポーネントとしてMDXから利用する。

既存サイトの一般設計: docs/brief.md、docs/requirements.md、docs/quality-bar.md。
FusionのConcept/Node/Recipeの境界: docs/fusion-authoring-contract.md。

## 最初の利用の流れ

Reference → 映像表現と画像処理 → Dithering等の用語 → 何が変わるか → Before/After → パラメータを1つ変えて試す → 実装の違い／関連表現 → ソフト別の再現方法。

「仕組みが何か」と「どのエフェクトを押すか」は別のページの責務とし、共通説明を二重に持たない。

## ファースト・スライス（P0）

- reference/visual-processing/index.md に日本語の用語索引を置く。
- サイドバー、Referenceトップ、横断検索から到達できる。
- 定義が「専門用語を別の専門用語に言い換えた一行」にならないよう、結果や見た目を具体的に書く。
- 分類は増分で改訂できる。全画像処理の完全網羅を初期受入条件にしない。
- 実験デモはまだ作らず、公開ページ上で「操作可能」と偽らない。

## P1：最初の実験ページ Dithering

最短の操作可能な教材を1つ作る。

- 入力: テストグラデーション（必須）および追加テストパターン（任意）。
- 手法: ディザなしの量子化、規則的ディザ、誤差拡散を最小構成で比較する。
- 調整: 量子化段数、方式、方式固有の大きさ／強さ、表示倍率。変更時は即時に再計算する。
- 出力: 処理前／処理後と拡大観察。リセット、現在の値、方式の簡潔な説明を用意する。
- 観察: 階調が減るとバンディングが出ること、ディザで粒子・規則模様と引き換えに段差が目立ちにくくなること。
- 明示: ブラウザ上の色表示・ガンマ・8-bit処理はAE/Resolveの内部処理やHDR結果の厳密なエミュレーションとは限らない。

P1の実験でCanvas 2Dを使用する想定。ただしP1開始時の具体的な性能と必要精度を見て決める。

## 再利用コンポーネントの境界

実際に2種類以上の教材が現れてから、共通化すべきものだけを抽出する。初期段階では汎用レンダリング・エンジンや宣言的なシミュレーション言語を設計しない。

共通化候補:
- Playground外枠・操作パネル・数値表示・初期値に戻す機能
- 元画像と処理結果の比較（切替、並列、wipe）
- パラメータの型／単位／範囲とプリセットのデータ表現
- 動画・音声の再生／一時停止／時刻移動
- 操作できない端末向けの静止画像・動画フォールバック

内容別の処理コアは分離する:
- 画素操作: Canvas 2D → 必要ならWebGL/WebGPU
- 時間方向: Canvas描画／Video Elementなど、性能を見て選択
- 音声: Web Audio API、ユーザー操作後に音を鳴らす
- ソフトウェア／機材: UIの状態遷移・入出力・制約のモデル。見た目だけの模倣と動作再現を区別する

Docusaurus / MDXはSSR時にもビルドされるため、window・document・AudioContext・Canvas等のブラウザAPIはクライアント側でのみ参照する。mount/unmountでイベント／アニメーション／AudioNode等を適切に開放する。

## 入力・表示に関する注意

- パラメータは意味と単位が分かる名称・数値を表示し、操作範囲と初期値を明記する。
- 色だけを状態表示に使わず、キーボードとタッチで操作できるようにする。
- 動画・音声を勝手に再生しない。reduced-motion環境では不要なアニメーションを停止する。
- スマホで主要な実験が使用可能であることを優先し、高負荷時は表示解像度を下げる等の段階的制限を可能にする。
- 画像・音源の権利・出典を明確にする。権利不明な制作物・映画フレーム等は無断で埋め込まない。
- 実機再現は、UI表面／操作反応／信号モデル／仕様準拠のどの段階まで再現したかを明示する。

## 受入と更新

### 今回（P0）

1. 新しいReference索引のURLが成立し、Referenceトップからたどれる。
2. 日本語サイドバーに馴染み、既存の検索・他のManualのURLを壊さない。
3. 主要項目に短いが観察可能な現象の説明がある。
4. 実験未実装を明示し、存在しないページへのリンクがない。
5. PRで差分とビルド／リンク結果を確認できる。

### 後続（P1）

- 量子化なし／量子化／ディザの相違が確実に観察できる。
- パラメータが画面に反映し、リセットや処理前後の比較が動作する。
- クライアント描画がサイト全体のビルドを妨げない。
- 実装が行っていない色管理・HDR等を保証しない。

### さらに後

異なる種別の2件目（例: Blur/Bloom）で共通UIを検証してから、汎用スキーマの採用と抽象化を判断する。Audioや機材は独立した実装境界が必要なら同じ見た目のコンポーネントを共有しつつ、演算エンジンは別にする。

公開・mainへの統合は既存リポジトリの公開方針に従い、初期作業はブランチ／PR上で評価する。
